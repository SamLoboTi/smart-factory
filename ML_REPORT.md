# Smart Factory Predictive Maintenance ML Report

Generated: 2026-06-03

## Executive Summary

This project now uses an initial predictive maintenance pipeline instead of a single
accuracy-oriented demo model. The pipeline covers:

1. industrial synthetic dataset generation;
2. failure prediction model comparison;
3. anomaly detection;
4. remaining useful life (RUL) estimation;
5. explainable inference;
6. model artifact versioning.

The main design principle is:

> Do not only show AI on a dashboard. Show a reliable predictive maintenance
> pipeline: data, model, metrics, explainability, and inference.

## AI Modules

### 1. Anomaly Detection

Model:

- Isolation Forest

Purpose:

- Detect whether a telemetry snapshot is outside the learned normal operating
  pattern.

Example output:

- "Current vibration and temperature are outside the normal operating pattern."

### 2. Failure Prediction

Models compared:

- Logistic Regression;
- Random Forest with hyperparameter search.

Selection criterion:

- recall for the failure class first;
- PR-AUC second;
- F1-score third.

This priority is intentional. In predictive maintenance, false negatives are
expensive because a missed failure can stop production, damage equipment, or
create safety risk.

### 3. RUL Estimation

Model:

- RandomForestRegressor

Target:

- tempo_ate_falha_horas

Current metric:

- MAE: 111.57 hours

This is a portfolio-grade first step. A production-grade RUL pipeline should use
real temporal windows per asset, maintenance orders, censoring, and possibly
survival analysis.

## Explainability

The inference layer now returns reasons such as:

- high failure risk detected by the predictive model;
- vibration above the historical safe range;
- temperature close to or above the operational limit;
- high accumulated operating hours;
- maintenance interval appears overdue;
- current telemetry outside the learned normal operating pattern;
- estimated RUL below 72 hours.

The next step would be SHAP for model-level feature contribution, but the current
rules already provide readable operational explanations.

## Limitations

- The dataset is synthetic and must be calibrated with real sensor history.
- Failure labels are simulated, not derived from real CMMS/work-order events.
- No SHAP integration yet.
- No model registry server yet.
- RUL does not yet model censored data.
- Model drift detection is not implemented.

## Next Steps

1. Add SHAP explanations for failure model predictions.
2. Add temporal feature windows per equipment.
3. Store model metadata in a registry table or MLflow.
4. Add threshold tuning by asset criticality.
5. Add drift monitoring for sensor distributions.
6. Replace synthetic labels with real maintenance events.
